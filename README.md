# MyTimetable

> Планировщик обучения поверх университетского расписания.

## Зачем появился проект

В следующем учебном году я планирую совмещать университет, обучение в Т-Академии и самостоятельное изучение backend-разработки.

Большинство существующих календарей позволяют только вручную создавать события. Для меня этого оказалось недостаточно: я хотел автоматически распределять собственные занятия по свободным окнам в расписании университета.

Например:

- убрать из плана необязательную онлайн-лекцию;
- автоматически освободить этот слот;
- распределить темы вроде «Базы данных», «Архитектура», «ASP.NET» по появившимся окнам;
- при изменении университетского расписания перестроить план без ручного редактирования.

Поэтому я решил написать собственную систему, чтобы пользоваться самому - с удобством и в угоду личной специфике. Мой проект — не просто расписание, а способ строить собственный план с опорой на существующие ограничения. Именно эта идея определила архитектуру проекта.

## Основные возможности

- автоматически получает расписание группы из TSU InTime;
- позволяет исключать необязательные занятия университета из собственного плана, сохраняя их в исходном расписании;
- автоматически распределяет собственные занятия по свободным слотам;
- поддерживает различные стратегии планирования;
- обнаруживает конфликты между пользовательскими занятиями;
- не теряет пользовательские данные после обновления расписания университета;
- быстро отображает расписание благодаря предварительному построению кэша;
- работает через Web и Windows CLI.

## Почему архитектура получилась именно такой

Главная сложность проекта заключалась в том, что расписание университета регулярно обновляется из внешнего API, а пользовательские изменения должны сохраняться независимо от этих обновлений.

Поэтому система разделяет:

- данные университета;
- пользовательские изменения;
- автоматически созданный план обучения.

Каждый слой имеет собственного владельца и обновляется независимо.

## Ключевые архитектурные решения

### 1. База данных — источник истины, кэш — только производное представление

Основной поток данных выглядит так:

```text
TSU InTime API
      │
      ▼
  CacheWorker ── обновляет DefaultLessons
      │
      ▼
  PostgreSQL
      │
      ▼
  ScheduleBuilder ── строит доменную модель
      │
      ▼
  CacheRebuilder ── рендерит и сжимает готовые ответы
      │
      ▼
  Controllers / Browser / CLI
```

Приложение сознательно использует стратегию **cache-then-serve**:

- дорогая работа выполняется при обновлении данных;
- чтение главной страницы сводится к отдаче готового gzip-блока;
- partial-представления дней также хранятся в памяти;
- после изменений кэш перестраивается немедленно;
- при старте сначала выполняется прогрев из уже существующей БД, а не сразу запрос во внешний API.

Это сознательный обмен: записи и изменения дороже, зато обычное чтение расписания быстро и предсказуемо.

### 2. Разные владельцы данных не перезаписывают друг друга

В расписании существуют три независимых типа состояния:

| Данные | Владелец | Поведение |
|---|---|---|
| `DefaultLessons` | API университета | полностью заменяются при очередном обновлении |
| `Deactivations` | пользователь | скрывают дефолтные занятия |
| `CustomLessons` | планировщик/пользователь | переживают обновление API |

Когда состав занятий в будущей неделе меняется, старые скрытия для этой недели сбрасываются. Сравнивается именно состав дефолтных занятий, а не весь объект дня — так изменение служебного массива `Cells` не создаёт ложную инвалидацию.

### 3. Планировщик работает по протоколу «предложение → решение»

Алгоритм не получает все правила предметной области. Селектор предлагает пару:

```text
(slot, subject) → Planner
```

Планировщик отвечает двумя независимыми флагами:

```text
(slot accepted, subject accepted)
```

Селектор механически реагирует на четыре комбинации:

| Ответ | Реакция |
|---|---|
| `true, true` | принять слот и предмет |
| `true, false` | оставить слот, попробовать другой предмет |
| `false, true` | оставить предмет, попробовать другой слот |
| `false, false` | заменить оба |

Благодаря этому правила вроде «не ставить в воскресенье» или «не допускать конфликт» находятся в `Planner`, а алгоритмы выбора не знают причин отказа.

Селекторы работают через `Peek`/`Commit`: внутреннее состояние изменяется только после принятия предложения. Это важно для корректных повторных попыток.

### 4. Выбор предмета и выбор слота — отдельные расширяемые компоненты

Обобщённый `DualSelector` собирается из двух фабрик:

```text
Picker  +  Slotter  →  DualSelector
```

**Pickers:**

- `roundrobin` — по очереди;
- `fairshare` — сохраняет пропорции очереди;
- `largest` — предмет с наибольшей оставшейся очередью;
- `smallest` — предмет с наименьшей очередью;
- `random` — равномерный случайный выбор;
- `weighted` — случайный выбор с весом по размеру очереди.

**Slotters:**

- `sequential` — ближайший свободный слот;
- `gap` — закрытие дыр в уже занятых днях;
- `emptyseed` — по одному занятию в пустой день;
- `leading` — расширение первой занятой группы к началу дня;
- `trailing` — расширение последней занятой группы к концу дня.

Кроме композиции, есть готовые стратегии (`gap`, `emptyseed`, `leading`, `trailing`, `roundrobin`, `fairshare`, `largest`, `smallest`, `random`, `weighted`). Так можно сравнивать готовый алгоритм с произвольной комбинацией picker/slotter.

### 5. Селекторы получают снимки состояния

`PlanningSelectorBase` копирует очередь предметов и список свободных слотов. Поэтому:

- селектор может свободно менять своё рабочее состояние;
- живая очередь планировщика не декрементируется дважды;
- композитные стратегии изолированы друг от друга;
- порядок предметов и исходные пропорции фиксируются в момент создания селектора.

`CompositePlanningSelector` последовательно запускает несколько стратегий, передавая следующей оставшуюся очередь и оставшиеся слоты.

### 6. Изменения применяются через changeset

Планировщик меняет доменную модель и одновременно формирует `ScheduleChangeset`. Затем `ChangesetApplier` переводит изменения в EF-сущности.

Это разделяет:

1. алгоритм принятия решения;
2. изменение рабочей модели;
3. запись в БД.

Changeset хранит последнее решение для каждого слота, поэтому применение идемпотентно. `SaveChanges` вызывается владельцем операции, а не самим `ChangesetApplier`.

### 7. Время можно сдвигать без ускорения фонового обновления

`Schedule:DateOffsetDays` подключается через `TimeProvider` и позволяет тестировать другой участок учебного года.

Особенность решения: планировщик и отображение используют сдвинутое время, а `CacheWorker` запрашивает API по реальному времени. Так отладка горизонта планирования не меняет расписание, которое фоновый процесс считает актуальным.

## Хранение данных

Основные таблицы PostgreSQL:

- `DefaultLessons(Date, LessonNumber, ...)`;
- `CustomLessons(Date, LessonNumber, ...)`;
- `Deactivations(Date, Number)`;
- `Users(Username, Password, IsViewer, IsEditor, ...)`;
- `Sessions(Id, Username, StartedAt, ExpiresAt)`.

У дефолтных и пользовательских занятий одинаковый составной ключ `(Date, LessonNumber)`, но это разные таблицы: внешний API не должен уничтожать пользовательские изменения.

## Авторизация

- браузер получает HttpOnly cookie `mytimetable.session`;
- CLI передаёт `X-Session-Id`;
- срок серверной сессии — 20 минут;
- просроченные сессии удаляются отдельным `SessionExpirationWorker`;
- `viewer` может смотреть расписание;
- `editor` дополнительно может скрывать занятия и запускать планирование;
- cookie использует `SameSite=Lax`.

При старте приложение применяет миграции и создаёт development-пользователей из `Program.cs`. Эти пароли нельзя оставлять в production.

## HTTP API

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/` или `/App` | главная страница расписания |
| `GET` | `/App/GetOne?date=...` | partial одного дня |
| `POST` | `/App/Login`, `/App/Register` | браузерная авторизация |
| `PATCH` | `/App/Hide`, `/App/Unhide` | скрытие/возврат дефолтного занятия |
| `GET` | `/Planner` | страница планировщика |
| `GET` | `/Planner/Strategies` | доступные стратегии в бинарном формате |
| `PATCH` | `/Planner` | выполнить планирование |
| `GET` | `/Planner/Conflicts` | получить конфликты |
| `PATCH` | `/Planner/ResolveConflicts` | убрать конфликтующие custom-занятия |
| `GET` | `/Cli` | бинарное расписание для CLI |
| `POST` | `/Cli/Login`, `/Cli/Register` | CLI-авторизация |
| `POST` | `/Cli/Logout` | завершение CLI-сессии |

Сжатые HTML и CLI-ответы сейчас используют `Content-Encoding: gzip`. Бинарный CLI payload после распаковки имеет формат:

```text
[4 bytes scroll target][2 bytes UTF-8 length][UTF-8 table]
```

## CLI-клиент

CLI написан на C и использует Windows `WinHTTP` и `ShellAPI`.

Особенности:

- один небольшой Windows executable;
- сессия самопатчится внутрь `.exe` в заранее подготовленную область `.data`;
- сохранённый план также переживает перезапуск CLI;
- расписание отображается в терминале Unicode-таблицей;
- `plan` — интерактивный редактор очереди и стратегий;
- `conflicts` и `resolve-conflicts` доступны без браузера;
- для удалённых хостов CLI требует HTTPS.

Сборка из каталога `MyTimetable.Cli` с MinGW:

```bash
gcc main.c -lwinhttp -lshell32 \
    -Os -s -flto \
    -fno-ident -fno-asynchronous-unwind-tables -fno-unwind-tables \
    -o mytimetable.exe
```

Примеры:

```text
mytimetable login --host localhost --port 8080
mytimetable schedule
mytimetable plan
mytimetable conflicts
mytimetable resolve-conflicts
```

## Быстрый запуск

Требования:

- .NET 10 SDK;
- PostgreSQL;
- для CLI — MinGW GCC и Windows SDK/библиотеки WinHTTP.

Задать строку подключения через User Secrets:

```bash
dotnet user-secrets --project MyTimetable/MyTimetable.csproj \
  set "ConnectionStrings:Default" \
  "Host=localhost;Port=5432;Database=mytimetable;Username=postgres;Password=..."
```

Запуск development-профиля:

```bash
dotnet run --project MyTimetable
```

По умолчанию development-профиль использует `http://0.0.0.0:8080` и настройки из `appsettings.Development.json`.

Проверка тестов:

```bash
dotnet test MyTimetable.slnx
```

## Конфигурация

```json
{
  "ConnectionStrings": {
    "Default": "..."
  },
  "Schedule": {
    "DateOffsetDays": 0,
    "AllowUntrustedCertificate": false
  }
}
```

`AllowUntrustedCertificate` разрешён только в Development и нужен для локальной работы с сертификатом российского CA. В production его включать нельзя: правильное решение — настроить доверие к сертификату на сервере или reverse proxy.

## Тесты

Тестовый проект покрывает прежде всего planning subsystem:

- базовый контракт селекторов;
- композицию picker/slotter;
- все основные pickers;
- стратегии закрытия дыр и роста chunks;
- `DayLayout`;
- changeset и поведение композитного планировщика.

Запуск выполняется обычной командой `dotnet test`. Интеграционные тесты полного HTTP → БД → cache pipeline остаются отдельным направлением развития.

## Ограничения

- сейчас поддерживается одна группа, захардкоженная в `TsuInTimeFetcher`;
- CLI рассчитан на Windows;
- внешний API может быть недоступен или требовать доверия к специфическому CA;

## Cледующие шаги

- development seed-пользователи должны быть заменены production-механизмом создания администратора;
